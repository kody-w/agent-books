Chapter 9 — Hosts and Portability

In this chapter: expose a Python handler through SDK MCP and compare host contracts without assuming every surface runs the same package unchanged.

9.1 Agent SDK custom tools: wrap domain logic in MCP

Run python3 claude/examples/09_hosts.py for the live Agent SDK invocation. This complete declaration is importable without making a model request:

from claude_agent_sdk import create_sdk_mcp_server, tool

@tool("review_draft", "Prepare a draft for human review; never send.", {"draft": str})
async def review_draft(args):
    return {"content": [{"type": "text", "text": args["draft"]}],
            "structuredContent": {"draft": args["draft"], "sent": False}}

server = create_sdk_mcp_server(name="book", tools=[review_draft])
print(server["type"])

The SDK creates an in-process MCP server. The live example passes it under the key book and allows mcp__book__review_draft. That name derives from the server key and tool name, not from an arbitrary Python variable. Custom tools and naming.

When: embed validated business operations in a coding agent without running a separate network server. The numbered example wraps the same pure reviewer used by the Messages workflow and records whether it really ran. Limits: MCP results use content, optional structuredContent, and isError; these are not the Messages API's tool_result envelope. Keep error translation and validation in the wrapper. An in-process server shares the application's process privileges, so do not equate “MCP” with isolation. Custom tool execution.

9.2 Agent SDK query(): one bounded task

import asyncio
from claude_agent_sdk import ClaudeAgentOptions, ResultMessage, query

async def main():
    final = None
    async for message in query(
        prompt="Draft a short library review request. Do not send it.",
        options=ClaudeAgentOptions(
            model="claude-opus-5-5", tools=[], max_turns=3, setting_sources=[],
        ),
    ):
        if isinstance(message, ResultMessage):
            final = message
    if final is None or final.is_error or final.subtype != "success":
        raise RuntimeError(f"No successful SDK result: {final}")
    print(final.session_id, final.result)

asyncio.run(main())

What: the Agent SDK runs Claude Code's agent loop and streams typed messages; query() is a convenient entry point for one task. When: an application needs a bounded agent operation instead of an interactive terminal. The explicitly empty tools prevents the example from editing or sending anything. Python Agent SDK.

Limits: a successful connection is not a successful task. Inspect the final result and any required tool events. Settings sources affect instruction, permission, and plugin loading; this isolated example opts out rather than silently inheriting a user's project configuration. Authentication and the SDK runtime must be available; installing Python imports alone does not establish live access. Options and result messages.

9.3 Agent SDK ClaudeSDKClient: a continuing application

import asyncio
from claude_agent_sdk import ClaudeAgentOptions, ClaudeSDKClient, ResultMessage

async def main():
    options = ClaudeAgentOptions(
        model="claude-opus-5-5", tools=[], max_turns=3, setting_sources=[],
    )
    async with ClaudeSDKClient(options=options) as client:
        for prompt in (
            "Draft a review-only library follow-up with the original Friday date.",
            "Later evidence says Monday. Revise while flagging the conflict.",
        ):
            await client.query(prompt)
            final = None
            async for message in client.receive_response():
                if isinstance(message, ResultMessage):
                    final = message
            if final is None or final.is_error or final.subtype != "success":
                raise RuntimeError(f"Incomplete turn: {final}")
            print(final.result)

asyncio.run(main())

What: an asynchronous client keeps a conversation across multiple queries and exposes interruption and runtime controls. When: a UI accepts corrections, permission decisions, or further tasks within the same conversation. Limits: drain the current response, including its result, before beginning the next ordinary turn. An interruption is not an undo of side effects already performed. Use the session resume/fork options from section 8.1 when a later process must recover the conversation. Client lifecycle.

9.4 Agent SDK permissions: availability is not approval

What: tools define available capabilities, allow rules pre-approve matching calls, deny rules block them, and permission modes determine how unresolved requests are handled. Exact configuration:

from claude_agent_sdk import ClaudeAgentOptions

options = ClaudeAgentOptions(
    model="claude-opus-5-5",
    tools=["Read", "Grep"],
    allowed_tools=["Read", "Grep"],
    disallowed_tools=["Bash", "Write", "Edit"],
    permission_mode="dontAsk",
    setting_sources=[],
    max_turns=4,
)

When: a noninteractive review operation must not acquire editing or shell access. Here tools narrows the available built-ins; allowed_tools alone would not do that. For a tool requiring application approval, use a can_use_tool callback returning PermissionResultAllow or PermissionResultDeny, and do not pre-approve that same tool. SDK permissions.

Limits: dontAsk denies calls that would require prompting but does not revoke inherently allowed operations. Allow rules can bypass the callback; deny rules take precedence. bypassPermissions is not a way to make an allow list exclusive. Paths and credentials still need operating-system or sandbox boundaries; SDK policy is not a complete multi-tenant isolation architecture. Permission evaluation.

What: a managed agent is a server-side definition of model, instructions, tools, and other supported configuration; a session instantiates work from that definition in an environment. Limits: Managed Agents is beta. Agent definition, environment, session, and executor are different resources. Creating the definition does not run a task. A session retains its configuration snapshot; changing the underlying agent does not silently rewrite an already running session. Explicit updates have state and workflow restrictions. 9.6 Managed Agents sessions: hosted state and streamed events

Use the real agent.id returned above in this continuation:

from anthropic import Anthropic
import os

with Anthropic() as client:
    environment = client.beta.environments.create(
        name="library-drafts",
        config={"type": "cloud",
                "networking": {"type": "limited", "allow_package_managers": False}},
    )
    session = client.beta.sessions.create(
        agent=os.environ["BOOK_AGENT_ID"], environment_id=environment.id,
        title="Synthetic library follow-up",
    )
    print(session.id)
    with client.beta.sessions.events.stream(session.id) as events:
        client.beta.sessions.events.send(session.id, events=[{
            "type": "user.message",
            "content": [{"type": "text", "text":
                         "Create draft.md asking for library-plan review. Never send."}],
        }])
        for event in events:
            print(event.type)
            if event.type in ("session.status_idle", "session.status_terminated"):
                break
    print(client.beta.sessions.retrieve(session.id))

What: a session persists transcript and agent state while the service coordinates model calls and tools. When: jobs must survive a disconnected UI or a client restart; reconnect to the saved session rather than treating an open socket as the only state. Open the stream before submitting the message so initial events are not missed. Session quickstart, session resources.

Limits: idle is not synonymous with success. Inspect its stop reason: permission requests, missing custom results, budget exhaustion, and completed turns all require different handling. A live stream does not replay missed events; recover from the paginated event history after reconnection. Sessions are stateful retained resources and are not eligible for zero data retention; transcripts persist until deletion. Set budgets and delete synthetic resources according to the documented lifecycle after testing. Session operations and retention, Managed Agents data boundary.

9.7 Managed Agents custom tools: pair events with results

What: the agent declares an operation; your code executes it when an agent.custom_tool_use event arrives and posts a matching user.custom_tool_result. Exact agent tool declaration:

custom_review = {
    "type": "custom", "name": "review_draft",
    "description": "Return a supplied library draft for review; never send.",
    "input_schema": {
        "type": "object", "properties": {"draft": {"type": "string"}},
        "required": ["draft"], "additionalProperties": False,
    },
}

Add it to tools in section 9.5. This handler is the corresponding event bridge inside your consumer; event is an actual parsed stream event:

import json
import sys
sys.path.insert(0, "claude/examples")
from common import execute

def answer_custom_call(client, session_id, event):
    if event.type != "agent.custom_tool_use":
        raise ValueError("not a custom-tool event")
    try:
        result = execute(event.name, event.input)
        is_error = False
    except ValueError as error:
        result = {"status": "error", "message": str(error)}
        is_error = True
    client.beta.sessions.events.send(session_id, events=[{
        "type": "user.custom_tool_result", "custom_tool_use_id": event.id,
        "content": [{"type": "text", "text": json.dumps(result)}],
        "is_error": is_error,
    }])

When: connect private domain logic to hosted orchestration without moving the implementation into a prompt. Limits: serve calls promptly rather than waiting for session idle; a workflow's thread can await your result while the overall session remains running. Deduplicate deliveries before any consequential operation and persist the actual result. A declared tool with no serving implementation can leave the task awaiting action. Custom tools need their own authorization; built-in tool permission policies do not replace checks in your own implementation. Custom tools, results while workflows run.

9.8 Managed Agents self-hosted workers: move execution, not inference

import asyncio
import os
from anthropic import AsyncAnthropic, beta_async_tool
from anthropic.lib.environments import EnvironmentWorker
from anthropic.lib.tools.agent_toolset import beta_agent_toolset_20260401

@beta_async_tool
async def review_draft(draft: str) -> str:
    """Return a supplied library draft for human review, never sending it."""
    if not draft.strip():
        raise ValueError("draft must not be empty")
    return "Not sent. Review this exact draft:\n" + draft

async def main():
    key = os.environ["ANTHROPIC_ENVIRONMENT_KEY"]
    environment_id = os.environ["ANTHROPIC_ENVIRONMENT_ID"]
    async with AsyncAnthropic(auth_token=key) as client:
        await EnvironmentWorker(
            client, environment_id=environment_id, environment_key=key,
            workdir=os.environ["BOOK_WORKDIR"],
            tools=lambda env: [*beta_agent_toolset_20260401(env), review_draft],
        ).run()

asyncio.run(main())

What: a self_hosted environment acts as a work queue. Workers on your infrastructure claim sessions, execute requested tools, and post results; Anthropic continues to run the agent. Create the environment with client.beta.environments.create(name="library-worker", config={"type":"self_hosted"}), provision its environment key, register the matching custom tool on the agent, and set BOOK_WORKDIR to a dedicated isolated working directory before starting this worker. Self-hosted environments, worker custom tools.

When: execution needs internal network access, particular packages, or your own sandbox policy. Always-on workers, webhook-triggered workers, and one sandbox per session are documented deployment patterns. Multiple isolated workers can serve a queue; choose capacity and workspace isolation deliberately rather than sharing an unrestricted directory across users. Worker deployment patterns.

The example registers built-in shell/file tools as well as the reviewer because it demonstrates the general worker pattern. If only the review operation should exist, omit the built-in toolset from both agent and worker configurations. “Never send” prose does not revoke a general-purpose shell's network access. Worker tool registration.

Limits: this is not fully local inference. Tool inputs and outputs still flow to Anthropic, and skills/memory are downloaded into the execution environment. The environment key keeps the API key off worker hosts but is itself sensitive. The SDK worker supports custom implementations; the CLI worker cannot register them. Tool catalogs are listed at startup and cannot gain new implementations in an already running session. Restart after reviewed catalog updates. Cancel worker tasks gracefully so in-flight memory changes can upload; killing a worker is not clean checkpointing. Worker lifecycle and boundaries, catalog update limits.

9.14 Managed memory stores: share selected durable context

What: managed stores hold addressable memories that sessions mount with an access policy. Example: this creates one store and seeds only a synthetic approved preference:

from anthropic import Anthropic
import os

with Anthropic() as client:
    store = client.beta.memory_stores.create(
        name="Library preferences", description="Approved draft-only conventions.",
    )
    client.beta.memory_stores.memories.create(
        store.id, path="/follow-ups.md",
        content="Library follow-ups remain drafts. Preserve conflicting deadlines.",
    )
    session = client.beta.sessions.create(
        agent=os.environ["BOOK_AGENT_ID"],
        environment_id=os.environ["BOOK_ENVIRONMENT_ID"],
        resources=[{"type": "memory_store", "memory_store_id": store.id,
                    "access": "read_only",
                    "instructions": "Consult the approved library conventions."}],
    )
    print(store.id, session.id)

When: multiple hosted tasks need a curated, governed context store. Limits: attach stores at session creation, not midway through a run; at most eight stores attach to a session. Each memory is capped at 100 KB and a store at 10,000 memories. Choose per-user or per-project stores intentionally; shared memory is not implicit tenant isolation. The SDK handles the memory API's agent-memory-2026-07-22 header separately from Managed Agents calls. Managed memory.

9.19 Workflow runs: observe parallel work to completion

What: hosted workflow runs have their own lifecycle and phases inside a session. Example: consume these exact event types in the session stream:

def update_open_runs(event, open_runs):
    if event.type == "workflow_run.created":
        open_runs.add(event.workflow_run_id)
    elif event.type == "workflow_run.status_ended":
        open_runs.discard(event.workflow_run_id)

Use an initially empty set while processing events; also handle workflow_run.phase_started and workflow_run.phase_ended for progress. 9.24 Exercise the destination

Application guidance: test each host separately for filesystem, networking, credentials, package availability, persistence, approval, and failure handling. The SDK wrapper above proves a declaration can be constructed; only its live invocation proves authenticated tool execution in that environment.

The useful portability unit is the domain operation plus its explicit contract, not the spelling of an agent label. A pure reviewer can be wrapped as a Messages tool, SDK MCP tool, or Managed custom tool without changing what “never send” means. Session transport, executor placement, credentials, and retention still change. Preserve those distinctions when choosing a deployment architecture. API tool boundary, Managed execution boundary.
