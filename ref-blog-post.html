The Caller Knows Nothing

The simplest idea in agent design, and why almost everyone, including the AI that helps me build, keeps missing it.

In short: an AI agent works best when the model calling it knows nothing about its insides. It sees a name, a description and a few typed parameters, nothing more. The agent's result comes back into the conversation, written to steer the next step. Because that conversation is a plain record, any step can be replayed later with more data. Anthropic ships most of these parts across separate features; one Python file can carry all of them at once. Below: the pattern, the rules, a comparison with SKILL.md, and a cited check against Anthropic's documentation.

When you need to remember something, you don't open a database. You don't look up a schema, pick a table, or decide which index to use. You just know you can remember, and when something in the conversation sounds important, you do. Later, the memory is simply there.

That's the whole idea. It's the pattern behind every agent in a Brainstem, and I've watched people and models talk right past it for months. This afternoon I watched it happen again, so I'm writing it down.

Two small files

A Brainstem (see The Personless Harness) ships with two memory agents. The first saves:

class ManageMemoryAgent(BasicAgent):
    metadata = {
      "name": "ManageMemory",
      "description": "Saves information to persistent memory for future
        conversations. You MUST call this tool whenever the user asks you to
        remember something ... or the information will be lost.",
      "parameters": { "memory_type": ..., "content": ..., "importance": ... }
    }
    def perform(self, **kwargs):
        # clamp, default, store; none of this is the caller's business

The second recalls. It doesn't even wait to be called: before every turn it puts what it knows straight into the context.

class ContextMemoryAgent(BasicAgent):
    def system_context(self):
        return "<memory>...what you already know...</memory>"

Look at what the model, the caller, knows about these. It knows a name, a sentence about what the thing is for, and a few parameters. That's all. It doesn't know there's a SQLite file. It doesn't know about clamping, deduplication, or how a timestamp is formatted. It doesn't need to. When the user says "remember my favorite color is blue," the model reaches for the thing in its context that sounds like remembering. When the next turn starts, the memory is already in front of it.

We just know we have something we can invoke in our current context that lets us remember, if that sounds important in the current conversation. That's it.

The rules

1. The caller knows nothing about the inside. Name, description, parameters. Storage, checks, shaping and formats stay hidden in perform().

2. The description is the whole interface. It says what's needed and when it matters. Every bit of quality you want lives there, not in glue code around it.

3. The caller has full liberty. The description invites; it never confines. The caller may put anything it judges useful into a parameter. The agent takes whatever comes and handles it, and that freedom is where the surprising, good behavior comes from.

How smart people get it wrong

Today I asked my AI collaborator to make our pipeline's lenses (small agents that each do one language job) "dynamic, with the caller armed to give the right information in the right shape." It came back with a careful plan. Its centerpiece was a shared caller: host code that would read each lens's contract and fill its parameters from the case, turning free-text fields into fixed lists of choices.

That's thoughtful, rigorous, and exactly backwards. It took a few corrections to get it there:

  • First wrong turn: cages. Turning every field into a fixed list of choices does give you the "right shape," and it kills the caller's ability to add what you didn't think to ask for. Constrain only where something downstream truly needs exact values.
  • Second wrong turn: a smart host. A caller that knows each agent's insides is coupling. Every new agent now needs host code. That's the machinery we were trying to delete.
  • The fix: nothing in between. The transcript is the input. The agents are loaded beside it. The model invokes what sounds right. Results come back into the transcript. Done.

It's the same reason Unix pipes worked. The tools knew nothing about each other, and they composed through a plain, shared stream. Here the stream is the conversation.

The evidence is in a chat log

I asked a small model to "just make up" an agent that drafts content from a chat transcript. Its first attempt, built from a thin description, returned count: 0 twice: empty. The second, built with a precise description (who reads the draft, what goes in it, nothing sent automatically), came back as a real tool. Same model, same plumbing. The only difference was the description.

The same log shows the other half. Several times the model said it had saved or recalled something when it hadn't, or said it hadn't when it had. The truth was in the tool log the whole time, outside its view. When a result doesn't come back into the conversation, the caller has to guess. So the loop has to be closed: whatever an agent does goes back into the context, the way memory does.

The transcript carries only what came out

Here is the part that makes it compound. The transcript doesn't hold the agent's insides, its prompts, or its working state. It holds only what came out: the relevant result of the agent that was just called.

When ContextMemory runs, what lands in the conversation is the handful of memories that matter, not the database. When LearnNew runs, what lands is "created TranscriptFollowUp, here's what it does," and on the next turn that new agent is hot-loaded, sitting in the context beside all the others, ready to be invoked. The conversation didn't just get information. It got a new capability.

So every step downstream starts from a better place. The next call sees the previous result and can build on it: use the recalled preference, call the agent that didn't exist a minute ago, refine the draft that came back. Nobody wired those steps together. Each one just leaves its output in the shared stream, and the next one picks up whatever helps.

4. The transcript carries only outputs. Each agent leaves just its relevant result. Nothing from inside it leaks, and nothing that matters is lost. Downstream steps use it to their advantage, and that's how the whole thing gets better as it goes.

The agent writes the next prompt

A tool's return value is usually treated as data, and the next move is left to a framework or the model. These agents return something written for whoever reads it next. Here is what a small Hacker News agent hands back:

{
  "status": "success",
  "stories": [ ...full records... ],
  "summary": "Top Hacker News stories:\n\n1. **[Title](url)** ...
              \n\nWhen presenting these to the user, render the titles as
              clickable markdown links exactly as written above.",
  "data_slush": { "count": 10, "top_url": "https://..." }
}

Three things travel in that one result:

  • A finished piece (summary), already shaped the way it should be shown. The code comment says it plainly: the model tends to copy this format word for word, so the agent writes it right once.
  • An instruction for the next step, inside the result itself: render these as links. The agent doesn't know who reads it next, and it doesn't need to.
  • A structured payload (data_slush) for the next step to use as-is, not for the model to reword.

The agent that learns new agents does the same. Its result says "created TranscriptFollowUp; it loads on the next request; re-run with submit to share it." The output carries the data, the instruction and, here, a new capability.

That's where the orchestration lives. Not in a graph, a router or a planner, but in the return values. Each agent steers what happens next by what it leaves in the transcript, without knowing who comes next. That's why one file can be dropped in and immediately work with everything else.

5. The agent writes the next prompt. Its result is shaped for the reader, carries the next instruction, and passes structured data along, so the steps coordinate through what they leave behind.

Time travel

There's one more thing this buys you, and I missed it until it was pointed out. The transcript is static: a plain record of what went in and what came out. The caller is a static loop with the agent loaded beside it. So any turn can be replayed.

That means you can go back. Rewind to the turn where the draft was written, add what you only learned later (the file that arrived Tuesday, the answer a downstream step produced, the agent that was learned three turns on), and run that turn again. The past step gets a second try with data it never had. You don't rerun the whole pipeline, just the one turn, and you can keep both versions side by side and pick the better one.

6. You can time travel. A static transcript through a static caller can be replayed from any turn, with more than it knew the first time.

"Isn't this just SKILL.md?"

People say so, and I see why. In both, the caller sees only a name and a description and decides when to reach for it. Both are a file you drop in, and both work with any model. But the similarity stops at the front door.

A skill teaches the caller how to do something. An agent does it for the caller. A skill makes the caller know more. This pattern keeps the caller knowing nothing. They're opposites at the one point this post is about.

They're not rivals, though. Skills are great for know-how a person wants to read and edit: long procedures, style guides, judgment. Agents win where you need the same result every time, a typed input, a clean transcript and replay. A skill can tell the caller when to reach for agents, and once a skill's procedure is stable, it can become an agent.

"Anthropic already does this." Let's check.

This is the debate I keep having, so I settled it the boring way: I had every claim checked against Anthropic's own documentation, with several independent reviewers trying to refute each one and a claim kept only when a majority couldn't. So the honest verdict: Anthropic built excellent parts, and if someone says "tools already hide their code," they're right. The claim here isn't that any single property is new. It's that one file carries all of them at once, on purpose: typed and described going in, hidden code inside, a result written for the next step coming out, creatable mid-conversation, and replayable as a fixed step. That combination is the pattern, and I couldn't find it anywhere in Anthropic's documentation.

To be fair about the limits of this check: docs change fast, and "I couldn't find it" rests on absence. Shaping a tool's result to steer the next step is a convention anyone can adopt in any tool, today. That's rather the point: it's not a feature to wait for, it's a way of writing.

Depth without the descent

In Own the Engine I wrote about Karpathy's funnel: most people will never climb down to the layer where AI really does the work by learning prompts, picking models and wiring tools together. They shouldn't have to.

The comparison above is that funnel in miniature. To combine what Anthropic offers, you learn roughly 25 separate concepts across four hosts: tool use, server tools, tool search, programmatic tool calling, the memory tool, context editing, caching, the MCP connector, skills, subagents, hooks, plugins, checkpoints, SDK sessions, Managed Agents, Cowork and more. Each one is good. Together they are a descent.

The pattern asks you to learn one thing: a file with a name, a description, a perform() and a result written for whoever comes next. It doesn't teach you the 25 concepts; it carries their properties for you. That's why I hold it to a bar of one hour to learn, and why the file runs on an engine you own rather than one you rent. Depth, without the descent.

Why it matters

If the caller has to know the insides, every agent is a project. If the caller knows nothing, an agent is a file you drop in. Anyone can write one, any model can use one, and agents you never planned to combine start working together, because each one just says plainly what it's for.

You don't build intelligence into the plumbing. You give the model things it can reach for, describe them well, and get out of the way.

It's that simple. That's why it's so easy to miss.
