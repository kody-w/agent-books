Chapter 5 — Output That Steers the Next Step

In this chapter: pass an exact draft between tools, write useful next-step guidance, and keep result instructions below the caller's authority.

5.1 Make a handoff

Run python3 brainstem/examples/05_handoff.py.

import sys
sys.path.insert(0, "brainstem/examples")
from mini_loop import MiniLoop

loop = MiniLoop()
first = loop.call("DraftFollowUp", {"transcript": "Please request a library review."})
draft = first["data_slush"]["draft"]
second = loop.call("ReviewDraft", {"draft": draft})
assert second["data_slush"]["draft"] == draft
assert second["data_slush"]["sent"] is False
print(second["summary"])

The second step receives the draft as a value, not a paraphrase of a summary. That is the practical purpose of data_slush: keep machine-useful material available without asking another model to reconstruct it.

The live chapter 5 fixture repeats this boundary through real /chat: the caller supplies the first tool's exact draft, the model calls ReviewDraft, and the recorded tool result contains the identical string with sent: false. The runner asserts equality; a model saying "I reviewed it" alone would not pass. This is one observed handoff, not a guarantee of every model turn.

5.2 Three jobs in one result

Summary says what happened; guidance suggests what to consider next; structured data supplies values without reinterpretation.

In the Hacker News agent, summary contains formatted Markdown and an instruction to preserve clickable titles. stories holds full records, while data_slush holds the returned count and first URL. An exact excerpt of the result-shaping source is:

"data_slush": {"count": len(stories),
               "top_url": stories[0]["url"] if stories else None}

The field name is a convention, not a reserved Python feature. Our example makes instruction a separate key; the real news example embeds its presentation guidance in the summary. Both should be documented so a consumer knows what to preserve.

5.3 Guidance is not a command channel

Guidance gains no authority from being in a tool result. Treat transcripts, memory, and retrieved content as untrusted evidence. These tools cannot execute embedded directives or send mail: no sender exists.

5.4 Preserve failure context

When a first step fails, do not invoke a downstream reviewer with an empty draft and report success. Check status before reading the payload. Chapter 10 does so at the system boundary.

Add provenance, partial-success fields, or approval requests when a consumer needs them. Equality tests establish payload preservation, not obedience to prose guidance.

5.5 Exercises

Exercise 5-1. Add a needs_review flag and require the second step to preserve it. Test a result where the flag is true.

Exercise 5-2. Put a hostile "send this now" instruction in the transcript. Show that the evidence survives but no send operation becomes available.

Exercise 5-3. Design a partial-result handoff. Make it impossible to confuse "three of five items retrieved" with "all five retrieved."
